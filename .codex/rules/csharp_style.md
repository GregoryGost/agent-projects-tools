# C# style rules

Apply this rule only when `CODEX_PROJECT.md` declares the `csharp-style` profile active, when the task directly changes C# style configuration such as `.editorconfig`, or when a requested C# change must follow an already active project style profile.

This rule defines formatting, naming, and language-style policy. C# language correctness remains the responsibility of `csharp_core.md` and `csharp-core`.

## Required skills

Use together with:

- `csharp-core`;
- `csharp-style`.

Required base rule:

- `.codex/rules/csharp_core.md`.

## Source precedence

Use this precedence:

1. repository `.editorconfig` and other explicit project style configuration;
2. project-declared style policy in `CODEX_PROJECT.md`;
3. established consistent source style where configuration is silent;
4. the portable baseline in `csharp-style` references only for new or unconfigured projects.

Do not reformat unrelated files or rewrite established conventions merely to match the portable baseline.

## EditorConfig policy

- Prefer `.editorconfig` for portable C# naming, formatting, and IDE language-style preferences.
- Preserve scoped sections and directory inheritance; do not add `root = true` without understanding the repository hierarchy.
- Treat style severity separately from preference. Do not promote suggestions or warnings to errors without explicit project policy.
- Preserve project decisions for `var`, qualification, expression-bodied members, braces, using directives, namespace style, modifiers, and other IDE rules.
- Do not assume Unity's compiler enforces every IDE style option merely because an IDE understands it.
- Keep Unity/engine analyzer and ruleset behavior separate from generic IDE style configuration.

## Naming baseline

When no project rule exists, use the portable baseline documented in `.agents/skills/csharp-style/references/editorconfig-baseline.md`:

- PascalCase for types and public/protected members;
- `I` prefix for interfaces;
- camelCase for parameters and locals;
- `_camelCase` for private/internal instance fields;
- clear boolean names such as `isReady`, `hasTarget`, `canMove`, and `shouldRetry`.

Static-field prefixes are project policy; do not force `s_` into an established Unity codebase solely because it appears in a Microsoft convention.

## Unity-safe style changes

When `unity-core` is active:

- do not rename serialized fields as a cosmetic style change without preserving serialized data;
- use `FormerlySerializedAs` or the project-approved migration path when an intentional serialized-field rename is required;
- do not rename Unity message methods, serialization callbacks, reflection-discovered members, menu paths, or other framework contracts;
- do not edit Unity-generated `.sln` or `.csproj` files as durable style configuration;
- keep Editor-only analyzer/ruleset integration within the Unity profile rather than assuming generic .NET build behavior.

## Change scope

- Format touched code, not the entire repository, unless repository-wide formatting was explicitly requested.
- Do not mix semantic refactors with mass formatting when that obscures review.
- Avoid formatter churn in serialized YAML, generated code, vendored code, packages, or code generated by Unity/framework tooling.
- Preserve line endings and file encoding policy declared by the repository.

## Review checklist

- [ ] `.editorconfig` and project style sources were inspected.
- [ ] Portable defaults were used only where project policy was absent.
- [ ] Naming and formatting changes do not alter public, serialized, reflected, or framework contracts.
- [ ] Diagnostic severity was not strengthened without authorization.
- [ ] Style changes are scoped and reviewable.
- [ ] Unity-specific style constraints were applied when Unity is active.
